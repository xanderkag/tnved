### По LLM-каналу

В skill: «Корпоративные данные — только в корпоративные каналы LLM. Передача в публичные `chatgpt.com`, `claude.ai`, личные подписки — не допускается. Корпоративные каналы (`llm.taipit.ru`, шлюз к внешним) находятся в разработке.»

У нас есть UI-форма для ключа — это даёт **три варианта**:

- **(a)** дождаться `llm.taipit.ru` или официального шлюза → подставить его base URL → ключ выдаёт ИТ;
- **(b)** деплоить с **пустым env** для ключа: тогда классификация падает с понятной ошибкой «настройте LLM в шестерёнке», каждый юзер вводит **свой** ключ → формально это «личная подписка», что skill запрещает; на пилоте/демо может пройти как осознанное исключение, но согласовать;
- **(c)** деплоить с ключом OpenAI/Anthropic в env (общий ключ на всех) → ровно тот же запрет skill'а, ещё хуже с точки зрения «корпоративные данные в публичный канал».

**Рекомендация:** идти вариантом (a). Если `llm.taipit.ru` недоступен — выкатывать только демо-режим (`demo_server.py`) под VPN, без передачи живых описаний наружу, до решения вопроса с каналом.

Применим, если Памятка ещё не введена в силу.

### A.1. Создать Deploy Token в GitLab

`Settings → Repository → Deploy tokens` → scope `read_repository`. Сохранить `username + token`. Один токен на проект — общих токенов нет.

### A.2. На прод-хосте (`10.10.13.10`)

```bash
ssh 10.10.13.10                       # либо алиас из ~/.ssh/config (имя — на твоё усмотрение)

git clone "https://gitlab+deploy-token-NNN:gldt-XXXXX@git.taipit.ru/airesearch/tnved.git"

# заполнить (см. вариант (a)/(b)/(c) выше про ключ):
#   LLM_PROVIDER=openai           # или anthropic
#   OPENAI_API_KEY=...            # либо ANTHROPIC_API_KEY=...
```

### A.3. Проверка

```bash
docker compose ps                  # оба контейнера healthy

# {"status":"ok","vectors":~15600,"groups":97,"static_version":"..."}
docker compose logs --tail=80      # без красных трейсбеков
```

### A.4. Запрос в ИТ-службу — шаблон

> Здравствуйте. Готовим к деплою на `10.10.13.10` новый сервис **tnved** (Ассистент по ТН ВЭД для декларантов).
>
> Прошу:
> 1. **Поддомен** `tnved.taipit.ru` (доступ из корп.сети).
> 2. TLS-сертификат на этот поддомен.
> 3. nginx server_block с `proxy_pass http://10.10.13.10:8082`.
> 4. `client_max_body_size 20m` — пакетная загрузка xlsx до 10 МБ.
> 5. `proxy_read_timeout 600s` — батчи на 500 строк могут идти до 10 минут.
> 6. WS-headers (`proxy_http_version 1.1`, `Upgrade $http_upgrade`, `Connection $connection_upgrade`) — у нас сейчас WebSocket не используется, но прошу прописать на всякий случай (это страховка для будущих доработок).
>
> Стек: FastAPI + Caddy в Docker, healthcheck `GET /health`. Спасибо!

### A.5. Открыть в корп.браузере

`https://tnved.taipit.ru` → три вкладки, шестерёнка → ввести ключ (если не задан в env), на вкладке «Один товар» вписать реальное описание → triage и финал должны вернуть **разные** коды для разных входов (в отличие от mock).

Если 502 / Bad Gateway → проверить с ИТ-службой `proxy_pass` (порт 8082 на хосте, healthcheck-эндпоинт).

## Если что-то не так (для маршрута A)

- **healthcheck падает 503** — посмотреть `docker compose logs app | grep FATAL`. Скорее всего FAISS/SQLite не собрались на этапе билда (TWS.BY 503'нула).
- **батч застревает на N/M** — провайдер таймаутит, см. `docker compose logs app | grep -i timeout`. Поправить `LLM_TIMEOUT` в `.env`, перезапустить.
- **«ставка не указана» у всех кодов** — TWS.BY не приехал во время билда. Закрыто B17 sentinel-чеком (билд падает) — если всё же прошло, сверить дату в `data/tnved.db` (`SELECT * FROM meta`).
- **браузер показывает старый JS/CSS** — закрыто B11 (cache-bust). Проверить: `curl -s http://localhost:8082/ | grep app.js` должен показать `?v=<хеш>`.
- **JS говорит "не настроено"** — нет ключа: открыть шестерёнку, ввести `OPENAI_API_KEY` или `ANTHROPIC_API_KEY`, сохранить. Либо положить ключ в `.env` сервера как fallback.
